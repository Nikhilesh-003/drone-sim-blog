WP1 · Motivation

Why put a flight controller in a game engine?

Gazebo is the usual simulator for ArduPilot and ROS. Open 3D Engine (O3DE) offers a different set of strengths:

  • Rendering quality. O3DE's Atom renderer produces realistic camera imagery, which is useful for vision and perception work.
  • Native ROS 2 support. O3DE's ROS 2 Gems provide sensors and robot controllers you can attach to objects in the editor.
  • An open integration problem. There's no ready-made ArduPilot connector for O3DE, so linking the two means designing the integration from scratch.

The goal of the project: a drone in a 3D scene, flown by ArduPilot, streaming a live camera feed, and able to fly missions planned in a ground control station.

SITL (software-in-the-loop) is the key piece. It's the same ArduCopter firmware that runs on a real flight controller, compiled to run on a PC with a simulator standing in for the real sensors and motors.

Every layer except one is off the shelf. The custom bridge node is what turns these separate tools into a working flight simulator.

WP3 · Architecture

How it fits together

The system runs as one closed loop. The simulator reports the drone's state, the autopilot decides what the motors should do, and the bridge turns that decision back into motion in the simulated world.

Every arrow in that loop passes through the bridge. Remove it and the simulator and autopilot have no way to reach each other. The bridge is also deliberately focused: it never sees the mission. Waypoints go straight from QGroundControl to ArduPilot, and all navigation decisions stay inside proven flight firmware. The bridge only translates data between the two systems.

WP4 · Simulation

The simulated world

In O3DE, a robot is built in the editor from entities and components and saved as a reusable prefab. The scene contains a ground plane, an environment with lighting and sky, and the drone itself.

The drone is a physics body carrying a set of ROS 2 sensors, including an inertial sensor, positioning and a forward-facing camera that streams live video into ROS 2. A detailed quadcopter model gives it a realistic look, while physics uses a simple shape to keep the simulation fast and stable.

WP5 · The key

The bridge node: the key to all of it

O3DE and ArduPilot were never designed to work together. No connector exists between them, and nothing in either project expects the other. The custom ROS 2 bridge node is what makes this project possible. Without it there's a game engine and a flight controller running side by side with no way to reach each other. With it, they behave as one flight simulator.

The bridge is the interpreter between the two systems, and it does that job continuously, many times per second:

  • Reporting state. It turns the simulator's view of the drone into the sensor data ArduPilot expects, so the autopilot believes it's flying a real aircraft.
  • Reconciling coordinate frames. Robotics software and flight controllers use different conventions for which way is up, north and forward. The bridge translates every value consistently.
  • Executing commands. It turns ArduPilot's motor outputs into motion the simulator applies to the drone, which closes the loop.
  • Keeping time and consistency. Both sides need to see the same vehicle at the same moment. The bridge keeps them in step.

Every capability the project shows depends on this one component: stable hover, autonomous navigation, GPS waypoints and complete missions. The rest of the stack is off the shelf. The bridge is the engineering that makes those tools fly together.

The autopilot handles control and the simulator handles motion. The bridge gives each job one clear owner and keeps the two systems in agreement, so they never compete.

WP6 · Navigation

From hovering to navigating

Holding altitude is the first milestone. Flying to GPS waypoints requires ArduPilot's state estimator (EKF) to trust its position and heading completely. In simulation that means giving it data that's clean and, above all, consistent: every value describes the same vehicle in the same place at the same moment.

Supplying that consistency is the bridge's job. Once the estimator is satisfied, ArduPilot's autonomous flight modes become available and the drone can fly missions over a real-world map.

A state estimator values consistency over realism. One reliable source of truth beats several sources that occasionally disagree.

WP7 · Results

Flying the mission

Missions are planned in QGroundControl over satellite imagery of Chennai and flown fully autonomously. The test mission is a loop: take off, fly to two waypoints in turn, then return to launch.

The drone climbs out, visits each waypoint in sequence and heads home, while O3DE renders the flight and the onboard camera streams to ROS 2. Firmware built for real aircraft is flying a vehicle that exists inside a game engine.

RTL · Summary

Key takeaways

Robotics fundamentals

  • Coordinate frame conventions are the foundation of every robotics integration.
  • State estimators need consistent inputs before they enable autonomy.
  • Each controller should own exactly one job.

Systems integration

  • The bridge between systems decides whether the whole works. It deserves the most engineering attention.
  • Several independent programs, connected over different protocols, can behave as one system.
  • Interfaces include more than names: timing, message types and delivery guarantees matter too.
  • A defined startup sequence is part of the design.

Engineering approach

  • Verify each link in the chain on its own.
  • Build observability in from the start.
  • Keep flight logic inside proven firmware. A focused integration layer does the rest.

Where it goes next

  • Higher-fidelity flight dynamics.
  • Richer sensor models.
  • Perception on the live camera feed.
